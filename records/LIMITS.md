# Admission, defaults and remaining hard constraints

## Overridable defaults and warnings

- No fixed frontend 256 MiB result, 2.5 GiB working, 128 MiB ZIP or frozen grid cap. Native package formats remain unchanged.
- Array/history working/retention estimates reuse the existing four-route inventory, with conservative full-volume estimates for the additional Static operations. They are not measured peaks or guarantees. Channel count, grid, slices and histories affect the estimate; FFT plans, allocator caching, solver iteration histories and driver overhead remain uncertain.
- Demanding means estimated new work above 60% of currently available memory. Available host memory already excludes resident allocations; resident charges are displayed separately, not blindly subtracted twice. Unknown host availability also requires acknowledgement. The explicit memory-risk checkbox permits proceeding despite conservative/unknown estimates. It does not override invalid inputs or invalid GPU telemetry.
- GPU working estimate/free/total is checked before admission and again in the worker. Demanding GPU estimates need acknowledgement. CPU does not probe CUDA. Numerical qualification requires a separate unqualified-execution opt-in, not a particular device model or request hash.
- The 600-second cooperative budget is editable; it is not a fixed product ceiling. Stop/timeout request cancellation at existing safe boundaries. No unsafe thread kill is promised.
- Preview defaults to 1,048,576 samples across channels, adjustable in Advanced. It controls only an independent editing image, never the scientific grid or Run qualification. Excessive display sampling explains how to raise that budget; it does not shrink scientific inputs.
- ZIP staging disk estimates also produce overridable warnings. Real filesystem errors remain errors. New filenames and overwrite protection preserve originals.

## Hard constraints retained and why

1. **Native numerical contracts.** Dataclass/codec validation, sampling/Nyquist rules, positive/finite required values, integrator/model combinations, precision requirements and versioned profile identities remain enforced. Full-transverse scalar optical projection still uses the engine's active component; UI controls cannot turn it into a new vector electro-optic model.
2. **Engine solver envelopes.** Unified connected direct solve has the native 12,288-active-node limit. Its scalable solver has native backend/precision/closure envelopes: current float64 ordinary limits are 2,048 per axis on CuPy, 1,024 on NumPy for general closures and 2,048 for unbiased; the versioned state32 profile has 96 NumPy / 256 CuPy limits, plus the engine's explicit 384×32 unbiased exception. These are engine-enforced commissioning limits, not this frontend's policy. Changing them needs a separate engine decision; no bypass was added.
3. **Current CUDA compatibility adapter.** Exactly one visible NVIDIA device, supported CUDA 12/13 CuPy distribution, driver/runtime checks, capability at least 6.0, stable identity/binding and correct tiny FFT dtype. The existing adapter imposes these checks; no broader compatibility is claimed. GPU free/total telemetry must be valid and fresh. Explicit GPU rejects incompatibility, binding, telemetry or precision failures rather than switching CPU. Float32 gets an additional complex64 compatibility check; local tests use mocks only.
4. **Demonstrably unavailable allocation/address space.** A required complex optical plane larger than available host/device memory is rejected; request precision determines the byte size. Serialized members must fit the process address space. These checks cannot guarantee successful allocation: host OOM/runtime termination may still occur despite estimates or acknowledgement.
5. **Portable format integrity.** Safe transport member names, no duplicates/path traversal, request/result checksums, native schemas and completed-package status checks remain. Runtime initial arrays belong in native state/transport/checkpoint formats, not experiment JSON. Some Static experiment codecs require an explicit backend and cannot serialize Auto intent; saving explains this rather than silently resolving it.
6. **Accepted-state continuation.** No Static Continue. Native compatibility fixes state layout, grid/material calibration/model/integrator/precision as appropriate. Existing physical-illumination continuation requires the engine's eligible host NumPy accepted state and compatible normalization/coupling; GPU continuation is not invented. A display preview or legacy file lacking accepted-state provenance is insufficient.
7. **Failure semantics.** Prior completed results are retained on cooperative Stop, timeout, rejected admission, file failure and Python allocation/execution failure. A killed Colab kernel cannot retain unsaved RAM; save files first for risky workloads. No frontend can promise survival of runtime deletion or external OOM termination.

The smallest remaining decisions are whether to commission a portable specialized image-analysis composite bridge, and whether Qt movie/table affordances need headless equivalents. Neither blocks ordinary four-route PR editing, execution dispatch, stored-result inspection or supported checkpoint operations. Current candidate and verification status are in records/READINESS.md and records/qualification/PR-CAPABILITY-READINESS.md. A prior hosted pass applies only to its exact kit; the rebuilt kit has local evidence only. No new numerical qualification is implied.
